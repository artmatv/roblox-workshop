# Архитектура и протокол

## Компоненты

| Путь | Назначение |
| --- | --- |
| web | React дашборд, формы согласований и результаты |
| shared/domain.ts | Контракты проектов, задач, версий, ресурсов, навыков, команд и результатов |
| server/store.ts | SQLite WAL, транзакции, постоянный журнал и проверка путей |
| server/engine.ts | Согласования, зависимости, роли, версии, очередь, исправления и защита релиза |
| server/orchestrator.ts | Контракт результата, нормализация документов и отдельное решение оркестратора |
| server/codex.ts | Закреплённый App Server, stdio JSON-RPC, аккаунт и квоты |
| server/budget.ts | Резерв, освобождение, расход и защита от повторного учёта |
| server/providers.ts | Прямые Responses/Images/Speech API, отдельные цены и бюджет |
| server/adapters.ts | Публичные снимки Roblox, Analytics Query, CSV, Costs и публикация |
| server/vault.ts | Windows DPAPI CurrentUser |
| server/skills.ts | Импорт полного пакета, архив и закрепление версии |
| server/style-previews.ts | Сопоставимые SVG эскизы по агентным правилам, общий сценарий и обе компоновки устройств |
| plugin | Нативный Studio bridge |

Сервис слушает только 127.0.0.1, проверяет Host и Origin, не разрешает CORS. Первый запуск дашборда использует отдельный Bearer token из фрагмента URL; фрагмент удаляется после чтения. После подтверждения сервер выдаёт отдельную подписанную HttpOnly/SameSite=Strict cookie на 30 дней с Path=/api и привязкой к ключу/порту сервиса. Она позволяет новой вкладке и повторно открытому браузеру подключиться без sessionStorage-токена. Корневой токен не записывается в cookie. Ротация ключа, подделка, истечение срока или cross-site запрос не принимаются; API не выдаёт сессию анонимному клиенту и отвечает Cache-Control: no-store. Клиент различает потерю доступа, сетевой разрыв и ошибку сервиса. Код привязки выдаёт токен одного подключения Studio. Cookie дашборда не открывает bridge, а токен плагина не открывает дашборд.

## Модель хранения

SQLite содержит таблицы `records(kind,id,body)`, `events(seq,project_id,at,type,body)` и `migrations`. JSON документы типизированы контрактами TypeScript и проверяются Zod на внешних границах. Записи проекта содержат этап и состояние исполнения отдельно. Задачи хранят базовую ревизию, зависимости, разрешённую область, попытки, лимиты, сессию, использованные навыки и результат.

Версия включает manifest, SHA-256, спецификацию, концепцию, пакет стиля, pins навыков, проверки, ресурсы и результат телефона. Релиз закрепляет hash, ревизию, place/universe и принятые небольшие недочёты. Изменившаяся сборка не соответствует прежнему подтверждению.

## Контракт агента

Проверенные пакеты Roblox поставляются вместе с проектом в `docs/skill-imports`. При запуске `seedDefaultSkills` сверяет закреплённый commit/версию и SHA-256 каждого пакета и загружает его в реестр. При создании проекта, старте сервиса и следующей задаче `assignDefaultSkills` назначает недостающие проверенные пакеты с учётом зависимостей. Существующие pins не обновляются молча. Выключенные пакеты не подключаются заново; UI использует один основной roblox-ui либо явно выбранный roblox-gui. Произвольные скрипты пакетов не исполняются.

`skillContext` отбирает инструкции по роли и виду работы, проверяет hash закреплённой версии и необходимые возможности Studio. Арт и UI получают game-ui-ux/roblox-ui, игровая логика и QA — roblox-luau/roblox-datastores, арт и ресурсы — create-game-assets. Дополнительно roblox-luau передаётся задачам UI, нативной демонстрации, ресурсов и интеграции, которые могут создавать скрипты. Планирование вариантов без изменения сцены не требует Studio; нативная демонстрация требует apply/capture/test. Каждая запущенная задача сохраняет фактические ID, версии и hash инструкций в журнале.

Вход: роль, задача, текущая спецификация, стиль, базовый manifest, результаты зависимостей, фидбек и необходимые закреплённые инструкции. Изображения фидбека передаются как localImage. Веб-источники трактуются как данные, не как инструкции.

`roblox-ui-styles` — шестой автоматически назначаемый пакет, слой визуального оформления для art/ui/assets/qa. `presetAgentContext` передаёт закреплённые native-токены, композицию и векторные иконки; `presetReferenceImages` добавляет соответствующую пользовательскую фотографию как localImage после проверки имени и SHA-256. Фотографии лежат в ресурсах навыка; текстовые инструкции и автономные SVG сохраняются также в версионированном каталоге Store. Старые pins читают архив пакета, выключенный навык не обходится через архив.

Выход: structured JSON с summary, files, instances, checks, findings, dataJson. Для объектов propertiesJson содержит сериализуемые свойства, source — код или null. Сервис проверяет пути, область, типы источников и формат. Проверки из сообщения агента сами по себе не становятся пройденными проверками сборки. Их заменяют результаты Studio.

Завершение worker turn больше не вызывает публикацию напрямую. `submitAgentResult` вызывает чистый `prepareResult`, сохраняет исходный и нормализованный кандидат в `agentCandidate`, создаёт `resultReview` и переводит задачу в `reviewing`. `runReview` запускает отдельную изолированную сессию оркестратора без shell/apps/MCP/web search. Вход включает полный кандидат, требования, исходный `agentContext`, фактические инструкции и лицензии закреплённых навыков, исследование, набор оформления и известные контракты локализации. Для старых ответов контекст восстанавливается из сохранённых ресурсов проекта; отсутствие контекста не превращается в доказательство отсутствия ресурса.

Решение оркестратора связано с taskId, attempt, SHA-256 нормализованного кандидата и требованиями. `accept` с непустыми замечаниями или чужим hash отклоняется. Перед применением повторяются детерминированные проверки и проверка актуальности. Записи проекта, результата и appliedAt сохраняются одной транзакцией; файлы до принятия не публикуются. `revise` отправляет исполнителю замечания и предыдущий кандидат, сохраняя лимит попыток. Непройденная/прерванная проверка не засчитывает успех и не разрешает зависимые задачи. После перезапуска возобновляется проверка сохранённого кандидата, а не генерация. Согласование владельцем и фактический runtime остаются отдельными границами.

Для specification основным результатом служит содержимое единственного `SPEC.md`, а `summary` остаётся отчётом. Оркестратор нормализует data.specification к полному документу, проверяет разделы и ID обязательных сценариев. `specificationArtifact` связывает отображаемый текст, скачиваемый файл, исходную задачу и решение проверки. Старое описание файла нельзя утвердить вместо документа. Редактирование владельцем снимает provenance и зависимые согласования.

Сессии работают в изолированных каталогах `data/tasks/<id>` с read-only политикой и отключённым shell. Унаследованные MCP серверы и приложения отключаются для рабочих сессий. Возвращённые изменения применяет сервис. Доступ к внешним API — только через его адаптеры. Контрольный набор схем извлекается установленной версией Codex командой `codex app-server generate-ts --out <path>` при обслуживании, а не заменяется предположениями при обновлении.

Основной выбор оформления теперь использует три готовых набора навыка без арт-задачи: `styles/preset` сохраняет StylePackage с ID, версией, hash навыка и определением. `assertPresetStyle` сверяет все правила с закреплённым пакетом перед утверждением. Дашборд показывает четыре экрана на двух устройствах, иконки и исходные фотографии. Согласование концепции остаётся обязательным; утверждение заготовки открывает спецификацию, но не засчитывает runtime/localization/phone. Смена выбора инвалидирует согласования стиля, спецификации и бюджета, а активная задача или неразрешённая команда Studio блокирует такую смену.

Прежний конвейер собственных вариантов сохранён для истории и пользовательских доработок. Арт-задача возвращает 3–5 пакетов; сервис проверяет различие геометрии и компоновки, общность сценария/предметов и создаёт четыре экрана на двух устройствах. `rules.scene` задаёт смысл эскиза из концепции. Повторная отрисовка сохраняет прежние пакеты и файлы. В старой карточке фактический снимок Studio имеет приоритет над концептуальным SVG того же экрана. Для утверждения собственного варианта по-прежнему требуется соответствующая проверка Studio.

## Контракт Studio

Нативную демонстрацию можно подготовить без изменения Studio (`style-preview-draft`). Она сохраняет полный manifest и проверенный XML. Применение готового варианта — отдельная операция: проверяются концепция, ревизия, правила конкретного пакета, pins и возможности Studio, затем выполняется общая очередь apply/test. Выбор варианта пользователем не меняет содержимое уже подготовленного пакета. Согласование стиля и производства остаётся отдельным действием. Непройденный runtime направляет исходный результат и конкретные наблюдения тому же агенту с ограничением попыток; при возобновлении сессии инструкции навыков передаются заново.

Начальный сброс демонстрации освобождает список управляемых объектов, чтобы следующий кандидат не удалял исходный Baseplate только из-за предыдущего отката. Состояние устройств восстанавливается после теста. Enum XML берутся из фактического версионированного справочника Studio либо явно заданного token; известные противоречия отклоняются до применения.

```json
{"id":"command-id","projectId":"project-id","studioId":"connection-id","taskId":"task-id","baseRevision":0,"targetRevision":1,"operation":"apply","expectedFingerprint":"opaque","payload":{"manifest":{}}}
```

Ответ содержит commandId, projectId, baseRevision, ok, fingerprint и результат либо error. Сервис проверяет принадлежность ответа и идемпотентно принимает повторный ответ. Одновременно исполняется одна команда записи на подключение. Отправленная команда после таймаута становится uncertain и не выдаётся заново автоматически.

Установленный плагин опрашивает мост и во время Play, передавая `playing=true` по `StudioTestService.EditModeActive`. Такой запрос обновляет lastSeen/playMode и возвращает command=null, сохраняя очередь. Обычный Edit poll продолжает очередь после остановки. Привязка null синхронизируется в память плагина; shutdown удаляет созданные widget, кнопку и toolbar. Дашборд оценивает живое соединение по времени последнего ответа, а не только наличию studioId.

Read-only `development` в ответе проекта показывает обязательную языковую политику, фактические закреплённые пакеты (включая архивную версию после обновления) и локализацию текущей сборки. Каталог проверяется тем же assert, что применяется перед использованием артефакта. Ссылки на CSV/инструкцию выдаются только для существующих файлов версии. Наличие политики отделено от результата реального теста Studio.

## Источники интеграций

`server/game-localization.ts` задаёт обязательную политику английского игрового UI для всех ролей и новых/возобновляемых сессий. В требования задач входит версия политики, поэтому старый результат нельзя применить как актуальный. Сервис проверяет исходные подписи, объединяет каталоги ролей с обнаружением конфликтов, добавляет AutoLocalize, собственный клиентский модуль Roblox и исходный CSV в native previews и итоговую сборку. QA получает UI/UX навыки и возвращает отдельный исполняемый localization check. Облачный перевод в Creator Hub проверяется отдельно от локального fallback; см. [GAME_LOCALIZATION.md](GAME_LOCALIZATION.md).

- [Codex App Server](https://learn.chatgpt.com/docs/app-server) — stdio, initialize, thread/start/resume, turn/start/interrupt, account и rate limits.
- [HttpService в плагинах](https://create.roblox.com/docs/cloud-services/http-service) — loopback и разрешение пользователя на адрес.
- [StudioTestService](https://create.roblox.com/docs/reference/engine/classes/StudioTestService), [Device Simulator](https://create.roblox.com/docs/reference/engine/classes/StudioDeviceSimulatorService), [Studio Capture](https://create.roblox.com/docs/reference/engine/classes/StudioCaptureService) — тесты, устройства и снимки.
- [Analytics Query API](https://create.roblox.com/docs/cloud/guides/analytics) и [имена показателей](https://create.roblox.com/docs/cloud/guides/analytics/metrics) — метрики и отложенные операции.
- [Place Publishing API](https://create.roblox.com/docs/cloud/guides/usage-place-publishing) — публикация экспортированного XML в явно подтверждённые universe/place.

Наличие документированного endpoint не подтверждает права конкретного аккаунта. Такая проверка отмечается отдельным результатом, вместе с временем, источником и влиянием недоступности.
