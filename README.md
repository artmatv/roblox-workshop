# Мастерская Roblox

*Local Windows workshop that builds Roblox games with AI agents (OpenAI Codex or Anthropic Claude Code), a Russian-language dashboard and a Roblox Studio plugin.*

Локальное приложение для Windows: русский дашборд, постоянный сервис, рабочие сессии ИИ-агента, очередь сборки и устанавливаемый плагин Studio. Агент работает через **Codex** (подписка ChatGPT) или **Claude Code** (подписка Claude) — исполнитель выбирается при запуске. Реализация по [ТЗ версии 1.4](docs/SPEC_SOURCE_RU.md).

## Требования

- Windows 10/11, Node.js 24.13 или новее.
- Roblox Studio и официальный Roblox Studio MCP — для сборки игр.
- Один из исполнителей:
  - **Codex CLI 0.167.0-alpha.3.2** и подписка ChatGPT;
  - **Claude Code CLI** и подписка Claude (Pro/Max).
- Для 3D/анимации — Blender 5.2 LTS, для Python-утилит навыков — Python 3.12 (необязательно).

## Запуск

1. Запустите `Start.ps1` (или `Start.bat`). При первом запуске устанавливаются закреплённые зависимости и собирается интерфейс.
2. Скрипт откроет личный дашборд на `http://127.0.0.1:4317`. Первый доверенный запуск подтверждает доступ браузера; далее обычный адрес открывается в новых вкладках автоматически. Подтверждение хранится 30 дней в подписанной HttpOnly/SameSite=Strict cookie и продлевается при использовании. Другому браузеру или профилю нужен свой первый запуск; неподтверждённый запрос доступа к проектам не получает.
3. В разделе «Аккаунты и расходы» подключите аккаунт исполнителя. Кнопка входа открывает официальный процесс входа; пароль приложение не получает.
4. Создайте проект и подключите отдельную Studio по [инструкции плагина](docs/STUDIO.md).

Закрытие браузера не останавливает сервис. Компьютер должен оставаться включённым и не спать. Остановка — `Stop.ps1`. Настройка автозапуска Windows не выполняется без отдельного действия пользователя. Для изменения порта используйте `Start.ps1 -Port 4318` и тот же адрес в плагине. Данные можно перенести через `AUTOMATION_DATA_DIR` для сервиса; вспомогательные скрипты по умолчанию используют папку `data`.

## Исполнитель: Codex или Claude

Исполнитель задаётся переменной `WORKSHOP_AGENT` (`codex` по умолчанию) или параметром запуска:

```powershell
.\Start.ps1 -Agent claude
```

Чтобы сменить исполнителя у работающего сервиса, остановите его `Stop.ps1` и запустите снова. Меняйте исполнителя между задачами: начатые сессии одного исполнителя другой продолжить не может, и задача начнётся заново.

**Codex.** Проверена версия **Codex CLI 0.167.0-alpha.3.2**; другие версии блокируют агентное исполнение до проверки совместимости. Мастерская запускает собственную копию из `.tools/codex/<версия>` (не обновляется вместе с Codex Desktop) или `CODEX_BINARY`. Вход, настройки и сессии хранятся отдельно от `~/.codex` — в `data/codex-home` (или `WORKSHOP_CODEX_HOME`); войти нужно один раз, через браузер или по коду устройства.

**Claude Code.** Сервис запускает `claude` из `PATH` или из `CLAUDE_BINARY` (нужен исполняемый файл, например `%USERPROFILE%\.local\bin\claude.exe` от официального установщика). Вход, настройки и сессии хранятся отдельно от `~/.claude` — в `data/claude-home` (или `WORKSHOP_CLAUDE_HOME`), поэтому ваши личные хуки, плагины и память в задачи не попадают. Войти можно кнопкой в дашборде или вручную:

```powershell
$env:CLAUDE_CONFIG_DIR = "$PWD\data\claude-home"; claude auth login
```

Работа идёт только по подписке: `ANTHROPIC_API_KEY` исполнителю не передаётся. Модели по умолчанию: Claude Opus 5.5 (`WORKSHOP_CLAUDE_MODEL` меняет модель по умолчанию); в политике sol-luna-astra роли Sol и Astra выполняет Opus 5.5, Luna — Sonnet 5.5. Уровень effort `xhigh` выполняется как `high` с записью причины.

Отличия Claude от Codex:

- нет встроенного `image_gen`: иконки создаются векторными через `draw_icon`, текстуры и меши — через `generate_texture`/`generate_mesh` Studio MCP;
- нет песочницы ОС: правки файлов разрешены только внутри рабочей папки задачи, а shell (Bash) доступен ведущему разработчику без сетевой изоляции;
- профиль motion-validation (проверка DCC-журнала команд) требует журнал Codex и с Claude не выполняется;
- лимиты подписки показываются по событиям Claude Code во время работы; до первого хода они неизвестны.

## Как устроена работа

Исследование → краткая концепция → выбор и утверждение готового пакета оформления → спецификация и оценка → ваши согласования спецификации и бюджета → производство → реальные проверки в Studio → фидбек → проверка на телефоне → подтверждение конкретной версии → публикация.

В «Концепции и стиле» доступны три заготовки из отдельного навыка [roblox-ui-styles](.agents/skills/roblox-ui-styles/SKILL.md): «Яркий симулятор», «Тактический tycoon» и «Неоновый clicker». У них разные композиции мира, навигация и подача предметов, 15 рисованных символов, HUD, меню, магазин и инвентарь на компьютере и телефоне. Можно рассмотреть экраны, наборы иконок и исходные фотографии. Кнопки выбора сохраняют ID, версию и отпечаток пакета. Для сравнения и утверждения заготовки не нужны Studio, агентная задача или генерация игры. Проверки готовой игры выполняются позднее и не засчитываются по эскизу.

Согласования проверяются кодом сервиса. Рабочая сессия не может подтвердить их за пользователя. Файлы, декларативная сцена и исходники проходят проверку структуры и разрешённой области. Геймплей, UI и ресурсы готовятся независимо; сборка в Studio проходит единую очередь. QA получает спецификацию и фактический manifest сборки, возвращает отдельный тестовый модуль. Непройденные сценарии создают ограниченную очередь исправлений. Некорректный ответ агента повторяется с причиной отказа до лимита попыток.

Каждый ответ исполнителя сначала получает проверку структуры, затем отдельную проверку оркестратором через ChatGPT. До принятия кандидат не меняет документы, зависимости, сборку и очередь Studio. Оркестратор получает полный результат, исходный контекст исполнителя, содержание закреплённых навыков, исследование, выбранный стиль и контракты сервиса. Замечания возвращаются тому же исполнителю с предыдущим кандидатом и ограничением попыток; при недоступной проверке кандидат сохраняется. Статусы и решения видны в «Плане и агентах». Проверка оркестратора не заменяет испытания игры в Studio.

Страница спецификации показывает полный проверенный `SPEC.md` с разделами и таблицами, позволяет скачать документ и перейти к редактированию. Краткий отчёт агента не используется вместо текста. Сохранённый старый ответ можно передать оркестратору кнопкой «Проверить сохранённый документ» без новой генерации. Ручное изменение документа снимает отметку проверки и согласования спецификации/бюджета.

Исходники игры и открываемый `place.rbxlx` сохраняются в `data/projects/<projectId>/versions/<revision>`. Приложение не требует готового жанрового шаблона. При расширении агент получает предыдущую версию, требования миграции и фидбек.

Roblox-навыки подключаются автоматически: game-ui-ux, roblox-ui, roblox-luau, roblox-datastores, create-game-assets, roblox-ui-styles, sypho-roblox-map, sypho-roblox-sfx, sypho-roblox-ui-tools, sypho-roblox-animation, sypho-roblox-3d-model и sypho-roblox-vfx. Сервис назначает проверенные пакеты новым проектам, существующим проектам при старте и перед следующей задачей, передаёт инструкции по роли и проверяет совместимость Studio. Ресурсы Sypho закрепляются вместе с инструкциями и материализуются в task workspace для изолированного использования. Арт, UI, ресурсы и QA получают выбранный пакет, его токены и векторные иконки; визуальные задачи также получают соответствующий исходный референс. Версии закреплены за проектом; обновление библиотеки не меняет их молча. Ручная установка навыков для обычного создания игры не нужна. Состав виден в разделе «Навыки», фактические инструкции — в журнале задач. Подробнее о границах всех двенадцати пакетов и статусе проверки новых motion-навыков — [документ интеграции Sypho](docs/design/SYPHO_MOTION_INTEGRATION.md). Проверка живой задачи для новых навыков пока ожидает финальных доказательств; прежние 16/16 gates не относятся к ним. История первого этапа находится в [старом документе](docs/design/SYPHO_SKILLS_INTEGRATION.md).

Все игровые интерфейсы изначально на **English (`en-us`)**. Генерация и сборка автоматически включают Roblox Localization: AutoLocalize, английский каталог и CSV, параметризованные динамические сообщения и английский fallback. Проверка `localization` обязательна; старые русские превью требуется обновить. Настройка облачного перевода опубликованного experience описана в [инструкции локализации](docs/GAME_LOCALIZATION.md).

В обзоре каждого проекта показаны правила разработки: фактически назначенные версии навыков, исходный английский язык и результат локализации текущей сборки. Каталог перевода и инструкция Roblox скачиваются из этой карточки после сборки. Само наличие правил не отображается как успешно пройденный тест.

Установленный плагин сохраняет живое соединение во время Play; команды остаются в очереди до остановки игры. В карточке Studio видны отсутствие связи и режим Play, доступны привязка и отвязка. Полный путь через браузер и установленный `.rbxmx` подтверждён в [product-flow.json](docs/verification/product-flow.json), без генерации новой игры или запуска агентов.

Для иллюстрированных игровых иконок и плоских текстур ведущий разработчик теперь может использовать встроенный **image gen** Codex. Созданный PNG автоматически сохраняется в рабочей папке проекта, добавляется в `assets/generated-images.json` и показывается в журнале. Сервис сопоставляет отпечаток рисунка с фактически загруженным PNG. SVG остаётся доступен для векторной графики и ранее созданных ресурсов. Подмена генерации примитивом при недоступном инструменте не считается готовым артом.

Визуальные варианты оценивает владелец: один предмет, сопоставимые размеры и фон, иконки также в 32/48 px, текстуры с повторением. Образец изображения не заменяет проверку его загрузки, материалов и вида в настоящей Studio. При изменении только небольшой детали не требуется заново генерировать весь набор ресурсов.

## Что проверено и что ещё требуется

Смотрите [отчёт проверки](docs/VERIFICATION.md) и [матрицу требований](docs/ACCEPTANCE.md). Успешная сборка приложения и тесты сервиса **не являются полной приёмкой по ТЗ**.

Проверен технический цикл: реальная задача Codex → автоматическое исправление ответа → сборка в согласованном Place1 → два Play/Multiplayer запуска в 1366×768 и 390×844 → доставка результатов через перезапуск сервиса → восстановление привязки → откат с совпадением исходного отпечатка сцены. Подробности — в `docs/verification/bridge-summary.json`. Экспортированный `place.rbxlx` открылся в отдельной Studio; установленный локальный плагин загрузился. Сквозной запуск использовал тот же исходник плагина через временный PluginManager; самостоятельный захват изображения требует отдельного разрешения Studio.

После уточнения пользователя от 2 ноября работа сосредоточена на плагине и дашборде. Развитие трёх контрольных игр остановлено; их материалы сохранены как тестовые данные. Выбор оформления игр сейчас не является условием использования или дальнейшей разработки инструмента.

Не объявлены пройденными: создание трёх законченных контрольных игр, по три доработки каждой, облачные сохранения и покупки, аналитика собственной игры, загрузка/модерация ресурсов, реальный телефон и публичный выпуск. Для них нужны согласованные проекты и соответствующие внешние доступы. Техническая сцена не заменяет эти критерии.

## Финансы и внешние источники

Подписочная квота, кредиты Codex/лимиты Claude, API баланс, гранты, организационные расходы и локальный бюджет разделены. Неизвестное остаётся неизвестным. Квоты берутся из `account/rateLimits/read` и событий App Server; время хранится в UTC и показывается в Asia/Bangkok. Сброс не устанавливает 100% без нового ответа источника.

Автоматический источник кредитного баланса API не подтверждён: доступен ручной ввод с датой и ссылка Billing. Costs API — отдельный административный ключ и отдельный учёт с пагинацией. Прямые Responses, Images и Speech API требуют ключа генерации, свежих подтверждённых цен и согласованного бюджета. Эти запросы сейчас не выполнялись. Их расчёт по usage или верхней оценке помечается отдельно от организационного счёта. Исчерпание подписки не включает API автоматически.

Аналитика Roblox использует официальный Analytics Query API; при недостаточных правах отображает недоступные показатели. CSV импорт сохраняет источник. Ключи шифруются Windows DPAPI CurrentUser и не включаются в инструкции агентов, файлы игры или логи.

## Проверки разработчика

```powershell
npm ci
npm run verify
node scripts/build-plugin.mjs
node --import tsx scripts/probe-codex.ts
```

`scripts/ui-verify.ts` — отдельный тест интерфейса на работающем сервисе; создаёт явно названный проверочный проект. Скриншоты и отчёты находятся в `docs/verification`. Он не запускает агентов, платные API и публикацию.

Пакет стилей пересобирается `node --import tsx scripts/build-ui-style-skill.ts`; после изменения его ресурсов обновите проверенный SHA-256 в `server/default-skills.ts`. `scripts/render-ui-style-skill.ts` проверяет геометрию текста 24 экранов; `scripts/verify-ui-style-skill.ts` проверяет выбор, сохранение, иконки и согласование через работающий дашборд без подключения Studio. Переносимый архив навыка: `outputs/roblox-ui-styles.zip`.

Для анимации персонажей, локальной Blender-обработки моделей и визуальных VFX-рецептов добавлены три пакета Sypho. Они дополняют существующие девять навыков: художественный стиль и происхождение остаются за `create-game-assets`, анимация не задаёт механику, VFX не задаёт урон. Проверенный локальный Blender — 5.2.3 LTS. Статус фактической проверки новых навыков и активной задачи описан в [заметке интеграции](docs/design/SYPHO_MOTION_INTEGRATION.md); прежние результаты 16/16 относятся только к первому этапу.

## Уровни effort исполнителей

Сервис явно задаёт effort при каждом `turn/start`, включая продолжение сохранённых сессий. Исследователь, арт-директор и ресурсы начинают с medium; геймдизайнер, геймплей, UI, QA и проверяющий оркестратор — с high. Сборка и операции Studio не вызывают модель.

Каждое содержательное отклонение оркестратора повышает следующий уровень на одну ступень, максимум до xhigh. Структурные ошибки, перегрузка модели, квота, таймаут и недоступность подключений effort не повышают. Для существующих задач учитывается сохранённая история отклонений. Завершённым и уже выполняющимся запускам новый уровень не приписывается.

В «Плане и агентах» можно отметить ожидающую задачу как небольшую точную правку (low), обычную, сложную (на ступень выше) или диагностическую. Ручной выбор требует причины; max допустим только для диагностики с сохранённым предыдущим запуском xhigh. Проверяющий оркестратор использует независимую политику high/xhigh. Поддержка уровня проверяется по каталогу моделей; при вынужденном снижении причина записывается, max молча не заменяется. Выбранная в проекте модель передаётся также при продолжении сессии.

В задачах и проверках сохраняются модель, effort, причина, номер попытки и время запуска. Эти записи вместе с usage и verdict позволяют сравнивать число исправлений, время и токены на принятый результат. Настройки effort не меняют согласования, бюджет и лимит попыток.

## Название проекта и варианты от ИИ

В обзоре рядом с названием находятся карандаш для ручного редактирования и «Придумать название». ИИ предлагает пять вариантов с объяснениями; выбор заполняет поле, а изменение применяется только кнопкой «Сохранить название». Переименование сохраняет ID, файлы, сборки, согласования и очередь работ.

Стиль основан на датированном снимке первых 24 игр официального Top Playing Now от 2 ноября 2026 года: `docs/research/roblox-name-study.json`. Список, источники и анализ доступны в панели названия. Основные приёмы — простое действие, цель и короткий образ; рекомендации генератора: английский язык, обычно 2–4 слова, без копирования названий, сезонных тегов и обещаний денег.

Варианты действительно создаются через уже подключённый ChatGPT/Codex, с effort medium. Передаются только текущий заголовок, жанр, идея и краткая концепция; полная спецификация, отзывы, файлы оформления и данные других проектов в запрос не входят. Проверка повторов с названиями других локальных проектов выполняется локально. При недоступности ИИ показывается ошибка, шаблонного запасного генератора нет. Одновременные клики по одному проекту объединяются; незавершённые запросы после перезапуска не повторяются автоматически.

## Продолжение после исчерпания попыток

Если проверяющий отклонил производственные задачи и лимит закончился, в обзоре и плане доступно «Исправить замечания и продолжить». Сервис создаёт ограниченную серию исправлений только для задач, блокирующих текущую сборку. Сохранённые кандидаты, замечания, сессии и история effort передаются исполнителям; готовые результаты и согласования сохраняются. Старые задачи остаются в истории и не запускаются повторно. Сборка переключается на новые зависимости; серверный контракт готовится до зависящих исправлений UI и мира.

Проверяющий оценивает вклад роли в её области записи. Исполнитель не должен реализовывать чужой UI, сервер или мир в обход scope через integration-файлы. Полнота и совместимость игры проверяются после объединения результатов и в Studio. Серия исправлений запускается явным действием владельца, не повторяется бесконечно автоматически и не обходит бюджет, актуальность согласований или сверку команд Studio.

## Точечная интеграция вместо повторной генерации всей сборки

Сервис собирает неизменённые принятые компоненты сам. Разные версии `docs/*.md` и `docs/*.txt` сохраняются в одном документе с указанием источников. Совпадающие объекты и файлы объединяются; противоречащий код, другие файлы и ключи локализации требуют явного разрешения. Удаления объектов, тесты, перевод и контракты ролей сохраняются.

Интегратор получает закреплённые `integrationBase`, `integrationBaseIdentity` и список конфликтов. Ответ содержит только изменённые полные объекты/файлы, явные удаления и `data.integrationPatch={baseId,baseHash}`. Сервис проверяет отпечаток основы и актуальность зависимостей, материализует полный кандидат, затем выполняет прежнюю структурную проверку и независимый review. Скрипт для будущего слияния не выполняется и не заменяет результат. Неизменённые ресурсы, каталог и код не нужно копировать в каждом ответе.

После содержательного отказа следующая попытка исправляет последний полный кандидат. При новом цикле интеграции создаётся чистая сессия, чтобы не переносить огромную историю неудачных полных пересборок. Поддержана повторная проверка сохранённого точечного исправления: оно материализуется на предыдущей полной основе и снова проходит оркестратора. Это не засчитывает ранее отклонённый результат как принятый и не заменяет Studio QA.

Планировщик не запускает второй раз активную задачу, ожидающую ответа настройки. Если все ожидающие цепочки заблокированы неуспешными зависимостями, статус показывает остановку; ожидание Studio, квоты и бюджета сохраняет свою причину.

## Ошибки экспорта и передачи на проверку

При подготовке результата и сборки ошибочный числовой token известного Enum приводится к значению из реестра, снятого с Studio. Смысл задаёт имя Enum; неизвестные значения не угадываются. Прямой XML-экспорт по-прежнему отклоняет противоречивые значения. Событие `build.enums.normalized` сохраняет конкретные исправления. Каждая попытка сборки учитывается до сериализации, поэтому ошибка экспорта расходует лимит и не создаёт бесконечный повтор.

Большой контекст независимого проверяющего передаёт точные повторяющиеся основы и ресурсы один раз, со служебной таблицей JSON Pointer. Все исходники, требования и кандидат сохраняются полностью; размер сообщения проверяется до отправки. Если чат без первой принятой реплики не сохранился у провайдера, сервис создаёт новую сессию только для проверки сохранённого кандидата, не повторяя работу исполнителя и не засчитывая новый результат без verdict.

## Один ведущий разработчик и создание ассетов

Новый режим производства по умолчанию — `single-owner`. Один постоянный чат Codex ведёт всю игру: ТЗ, мир, сервер, интерфейс и художественные ассеты. Рабочая папка находится в `data/projects/<projectId>/workspace`; ТЗ, референсы, исходный снимок и закреплённые навыки читаются из файлов. Исполнитель может редактировать рабочие файлы и пользоваться инструментами Studio вместо генерации всей игры одним JSON-ответом. Старые распределённые задачи остаются в истории; режим `distributed` доступен явно для прежнего процесса.

MCP-мост `workshop` запускает установленный StudioMCP Roblox. Он проверяет документ выбранного проекта и принудительно направляет все действия в связанную Studio. После паузы новые действия блокируются. Для иллюстрированных иконок и текстур агент может использовать встроенный `image_gen`; SVG через `draw_icon` подходят для векторной графики. Перед каждой новой загрузкой PNG агент обязан вызвать `inspect_image`: локальный предпросмотр показывает иконку на светлом/тёмном фоне в малых размерах или текстуру повторённой 2×2. Загрузка разрешена только для тех же проверенных байтов; после правки нужен новый предпросмотр. Проверка не оценивает качество автоматически и не требует повторной генерации без фактического дефекта или отзыва. Важные 3D-объекты создаются через настоящий `generate_mesh`, а их текстуры — через `generate_texture`. Произвольные внешние серверы и делегирование другим агентам в этом режиме не включаются. Это правило проверки выбрано после одного парного пилота на деревянной текстуре; оно не доказывает общего улучшения качества. Владелец предпочитает объёмные, хорошо читаемые иконки с выразительными бликами и текстуры с заметными деталями материала; палитра и тема выбранного проекта остаются основными. Если доступен `docs/design/visual-quality/approved-icon-b.png`, ведущий получает его только как референс отделки, не как утверждённый новый стиль.

Инструменты сохраняют оригиналы рисунков и журнал реальных действий. Снимки `screen_capture` отдельно сохраняются хостом вне рабочей папки агента, с фактическим устройством и viewport. Для предложения результата нужны реальные кадры мира, HUD, магазина, коллекции и телефона, созданный mesh, нарисованный и загруженный PNG, подключённый к настоящему GUI. Эти условия подтверждают выполненные действия и наличие материалов, но сами по себе не оценивают художественное качество. Оно обсуждается с владельцем по реальной игре и снимкам. Замечание в карточке «Ведущий разработчик» передаётся в текущий turn через `turn/steer`; после завершения следующий проход продолжает тот же чат и рабочую папку.

По завершении сервис делает снимок текущей Studio и сохраняет контрольную версию с mesh-материалами и исходниками. Результат получает статус визуальной оценки владельцем, все неподтверждённые игровые проверки остаются `not_run`. Счётчик успешных unit-тестов не является оценкой оформления. Публикация и продажи по-прежнему управляются отдельно.

Основа архитектуры: [Codex как платформа](https://developers.openai.com/blog/codex-as-a-platform) и [протокол App Server](https://learn.chatgpt.com/docs/app-server).

### Распределение моделей (sol-luna-astra-v1)

Новые проекты используют Sol 6.1 Medium для ТЗ, ведения игры и приёмки; Luna Medium — для кода по конкретной спеке. Astra Medium доступна только для проектирования и независимого разбора архитектуры. Предыдущие проекты сохраняют прежнюю политику до явного переключения в плане работ. Смена политики не изменяет выполненную историю и не возобновляет паузу.

Ведущий единолично применяет изменения к Studio. Инструмент `ask_specialist` запускает отдельную сессию через существующий Codex App Server, с отключёнными MCP, shell, сетью и делегированием. Модель получает выбранные локальные файлы и ТЗ; Luna возвращает код только для разрешённых путей, Astra и проверяющий — разбор без записи файлов. Ведущий принимает результат и проверяет настоящую игру. Это изолированные помощники через инструмент, встроенный collab с наследованием Studio выключен. Один запрос к помощнику за раз, без автоматических повторов или повышения effort.

`AGENTS.md` и инструкции harness закрепляют KISS/YAGNI, повторное использование существующего кода и запрет ненужных сред, копий реализации, резервных копий и процессных этапов. Сохранение результата и защита игровых данных остаются обязательными. Архитектурный кросс-чек нужен для существенного изменения архитектуры; обычная правка не создаёт отдельный обязательный этап.

Основание: [гайд по процессу разработки](https://realaillusions.com/ru/materials/sovety_ai_praktika_part3/) и [официальные ограничения наследования инструментов у подагентов](https://learn.chatgpt.com/docs/agent-configuration/subagents).

### Независимая проверка LLMASS

В «План и агенты» находится панель «Независимая проверка». Нажмите «Загрузить модели»: каталог берётся с `https://llmass.arbitron.dev/v1/models`, включая `context_window`, `max_output_tokens` и доступные маршруты OpenAI-совместимого API. Неизвестные лимиты не выдумываются. Сохраните свой ключ, выберите модель и включите проверку. Ключ хранится через существующий Windows DPAPI Vault и не возвращается в состояние UI, инструкции агентов или переменные MCP.

Ведущий получает `ask_external_review` при следующем запуске. Запрос идёт через локальный маршрут с ограниченным токеном конкретной задачи: проверяются активная задача, проект и Studio; сервер читает только выбранные файлы рабочей папки. Ответ — недоверенный независимый разбор; он не редактирует Studio и не заменяет приёмку Sol или визуальную оценку владельца. Пауза отменяет ожидающий запрос. Контекст и бюджет проверяются перед обращением к API, повторы и смена модели автоматически не выполняются. При неопределённом исходе резерв сохраняется до сверки.

Проверка сторонним API использует согласованный бюджет проекта. Само добавление ключа и загрузка каталога не запускают платную генерацию.
